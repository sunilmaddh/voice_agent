CURRENT WORKFLOW AND LOCKED LIMITATIONS
1. The complete command "decline the call and text I will call you later"
   authorizes one fixed reply for exactly one ringing call. Source permits this
   explicit voice path while locked. A short/incomplete or negated command is
   not equivalent authorization. Anyone able to invoke the locked assistant
   may request this fixed reply where prerequisites are satisfied.
2. Requires Android 11+, default Phone role, SEND_SMS, READ_PHONE_STATE, a visible
   usable tel number and an identifiable incoming-call subscription. Hidden
   numbers, invalid handles and ambiguous/multiple ringing calls are blocked.
3. SmsManager submits the SMS on that subscription. CALL_REPLY_SMS_PENDING means
   submitted/waiting, not sent or delivered. The API's sent callback establishes
   Android send success; recipient receipt requires separate observation.
4. RESULT_OK permits Call.reject(false, null) only for the same still-ringing
   eligible call within 60 seconds. Duplicate callbacks cannot decline twice.
   Failures/timeouts do not initiate decline; a late success can mean an SMS
   was sent while the call remains unchanged. An already submitted SMS cannot
   be recalled. There are no automatic send retries.
5. Manual call-screen review requires unlock. Previously enabled automatic
   driving replies are a separate path with their own settings. The persisted
   outcome cannot identify which of these paths generated it.
6. Ringtone silencing/wake handoff mitigates competing audio, but does not prove
   recognition works during ringing. Screen-off invocation, Bluetooth, dual-SIM,
   carrier restrictions and OEM lifecycle behavior require physical trials.

SPOKEN-MESSAGE TECHNICAL FEASIBILITY
A. Ordinary installed APK answering a SIM call and injecting a recording: 🔴 RED.
   Android Call.answer can request answering, and InCallService can control call
   endpoints [1][2]. These controls do not provide a public stream for sending
   arbitrary recorded audio into the cellular call. Current AOSP provides an
   uplink-injection SystemApi guarded by CALL_AUDIO_INTERCEPTION and explicitly
   reserved for privileged system apps [3]. AOSP routing tests also establish
   that ordinary playback cannot route to telephony uplink without privileged
   permission [4]. Assessment: the existing APK/default Phone role is insufficient.
   Local TTS/MediaPlayer playback is not a supported guarantee that the caller
   hears a recording. Speaker-to-microphone coupling would be unreliable with
   noise, echo cancellation and headsets and is not recommended as a workaround.

B. Hosted telephony/IVR with a service number or carrier forwarding: 🟠 AMBER.
   This is a technically supported alternative: a service handles the incoming
   call and plays the recording on its own voice connection. Twilio documents
   incoming-call webhooks and the Play instruction for caller-facing audio [5][6].
   Feasibility is established at architecture level, not for this user's SIM or
   deployment. Requires compatible number availability or carrier forwarding,
   hosted configuration/media, applicable account setup and recurring service/
   carrier charges. Regional availability and forwarding behavior need checking.
   Phone lock does not govern server playback once a call reaches the service.
   A per-call spoken command on the phone to divert/control that call introduces
   extra signalling and timing requirements; static forwarding is not equivalent
   to Aiko answering the original SIM call on demand. No provider was selected.

C. App-owned VoIP/SIP media: 🟠 AMBER.
   Feasible in principle when Aiko or its telephony backend owns the call media
   and can transmit recorded audio. This is an architectural inference, not an
   existing Aiko capability. It requires a VoIP service/media implementation;
   callers to a normal SIM number need a compatible gateway/forwarding setup.
   Phone-side locked operation still needs background/network/device validation.
   Telecom registration alone does not transfer control of cellular media.

D. OEM/system integration: 🟠 AMBER.
   Privileged AOSP audio access offers a conditional route [3]. Requires OEM
   system integration, permission allowlisting and compatible call-audio support;
   not a portable installation or a default-dialer permission upgrade.

DECISION AND REMAINING DEVICE ACCEPTANCE
Keep SMS reliability AMBER: user-reported locked operation is conditional on
silent/vibration mode, and audible-ringtone operation is RED. Silent/vibration
mode is a demonstrated test condition, not a validated universal fix. Confirm
recipient delivery, actual decline and repeated success in each mode before
claiming reliable locked end-to-end behavior. Diagnose audible-ringtone listening
using activation, microphone and audio-focus evidence before selecting a fix.
Keep prerecorded SIM-call audio RED for this APK. Investigate service-side voice
or OEM integration only if its deployment constraints meet the product need.
No recording injection, speaker workaround or replacement telephony stack was built.

Use a consenting test caller and record at least five screen-on locked trials and
five screen-off locked trials with the exact voice command. This is an initial
acceptance sample, not a statistical reliability guarantee. For each, record:
  ringtone/silent/vibration mode; lock state throughout; invocation/recognized
  command; SMS callback/result code;
  caller-observed message and receipt time; actual decline/disconnect;
  any unlock prompt; time from end of command to send result and decline.
Compare audible-ringtone, silent and vibration modes in locked and unlocked
states, recording listening failures separately from SMS-send failures.
Include cancellation, caller hangup/answer before receipt, duplicate commands,
hidden caller, missing permissions, and each available SIM where practical.
Use buttons/unlocked review as a separate baseline to distinguish voice problems
from carrier/SMS problems. No send-before-success decline, wrong-recipient SMS,
duplicate send or unrelated-call decline is acceptable. Report counts and failures,
not just the last successful status. Detailed phone outcomes remain pending;
conditional operation and audible-ringtone listening failure are user-reported.
